# Google Drive ACL refresh candidate

Base reviewed: `0ssol1620-byte/tavonel-saas-foundation` at `8944cbfb0335f3120c71dc823b4106da5de4a6af`.
This is a task-owned candidate; it is not applied to the repository, is not deployed, and does not turn on the existing viewer-ACL feature flag.

## Decision

Use a bounded background refresh queue. A request-time refresh would put Google permission-list latency and 429s on ordinary document reads, and a read over up to 2,000 document IDs could induce up to 40,000 provider page requests at the current 20-page per-file bound. A background worker can apply a fixed item/page budget, honor provider backoff, deduplicate by workspace + connection + immutable source-version, and refresh unchanged files without re-importing file bytes or reserving compute.

The durable sync cursor remains a source-change cursor. An empty `changes.list` page does not trigger source import today, and manual sync resumes that cursor, so neither is a reliable ACL refresh timer. The queue candidate independently scans current immutable Google Drive bindings and selects those whose latest snapshot is missing, incomplete, future-dated, or at least two thirds through its configured freshness window. At the 300-second default this starts refresh near 200 seconds. Queue insertion is unique per workspace/connection/source-version; concurrent scans coalesce.

The worker performs no `files.get` download, export, R2 write, OCR, or compute reservation. It reads only `permissions.list` metadata, with the existing maximum of 20 pages × 100 permissions and 2,000 direct principals per source. SQL rejects claims above five, while the adapter claims only work that fits the remaining per-turn budget (currently at most one). Metadata pagination remains capped at 20 calls per source; an end-to-end abort bounds work to 38 seconds and leaves 22 seconds before the route's 60-second maximum for persistence and lease settlement. Every item rechecks customer-data admission, active connection/consent, and that the immutable version is still the unique current binding both before obtaining an access token and before storing a complete snapshot. Failure to prove those checks cancels the job before ACL fetch or persistence.

The existing snapshot table has a content-only unique constraint, and the existing writer treats an identical hash as a no-op. That prevents unchanged files from becoming fresh. The queue SQL asserts and drops the exact verified constraint name `source_acl_snapshots_source_version_id_provider_id_snapshot_key`, then appends one immutable observation per complete capture, including unchanged content. The viewer-boundary writer also appends complete and incomplete observations without conflict handling. Existing pinned snapshot rows and timestamps remain intact; task 20's current-ACL check must evaluate the newest observation and accept an equivalent same-principal grant without replacing the async job's historical evidence. The disposable pgTAP fixture checks that a same-hash recapture adds a row, leaves the pinned row unchanged, appends an incomplete marker, denies viewer access, proves a newer complete capture supersedes an older incomplete marker, schedules tied complete/incomplete newest captures, continues cleanup past a terminal low-ID row, and continues work on an unrelated connection during cooldown.

## Authorization and async queue binding

Async jobs keep their historical `acl_snapshot_id`, hash, and capture timestamp unchanged. At each authorization checkpoint they also check the latest ACL snapshot for the same exact workspace, connection, source-version, and linked Google principal. A newer complete snapshot that still grants that principal does not invalidate a queued job merely because its snapshot row ID/hash/time changed. A removed grant, missing/incomplete/stale/future latest snapshot, revoked viewer link, inactive membership or changed membership revision, inactive/revoked connection, tombstoned source, or non-current source-version still denies. A newly granted principal does not retroactively replace the principal bound at enqueue. The ACL authorization SQL/test delta owned by task 20 is a dependency; this candidate must not be integrated against an async worker that still requires the pinned row to remain the latest row.

Provider-side viewer identity remains separate: a verified, unrevoked Google viewer link must still be within its existing 24-hour lifetime. File ACL refresh does not renew it. Expired identity requires the existing explicit OAuth verification flow.

## Backoff and fail-closed behavior

The queue stores `next_attempt_at` and releases a lease with a delay instead of sleeping in a worker invocation. A 429 honors a valid `Retry-After` seconds/date value capped to 900 seconds; missing/invalid values use bounded exponential backoff, also capped at 900 seconds. The capture helper propagates provider status and `Retry-After` in a typed error so the worker can persist a connection-scoped cooldown. Partial/malformed permission pages must never be stored as complete. A definitive incomplete capture appends an incomplete marker; if that write fails, the adapter reports `ACL_REFRESH_INCOMPLETE_MARKER_PERSIST_FAILED` and retries the lease. Viewer denial from the marker applies once persistence succeeds; the worker does not claim immediate revocation while the database is unavailable. Connection-scoped cooldown persists across claims and turns, while unrelated connections remain claimable. Queue freshness combines every observation tied at the newest timestamp and treats the source as incomplete if any tied row is incomplete, matching the reader authorization rule.

Current fresh snapshots continue to serve until they reach the configured max age; the worker does not make reads wait for provider calls. Once a snapshot is stale, reads remain fail-closed while retries are pending. No fallback to an older snapshot is allowed.

## Operational prerequisite

The reviewed base has no ACL-only scheduler or queue runner. This candidate now includes a bounded adapter and one-turn internal route, but it does not schedule itself. The route calls the same shared Bearer authorization helper used by the existing sync worker (`FOUNDATION_WORKER_SECRET` or `CRON_SECRET`), and the existing worker route is changed only to use that helper. It adds no credential and does not configure a schedule. A trusted scheduler still must invoke enqueue + claim/worker at a cadence that fits the eligible file count and configured age. Since refresh starts at two thirds of the age window, the worker has only the remaining one third to finish before old evidence becomes stale. The current one-claim turn bound does not prove backlog or freshness capacity; measure eligible inventory, provider latency/429 rates, polling cadence, and worker concurrency, then demonstrate headroom before making any capacity claim. Never represent the candidate as recurring until the scheduler is configured and observed operating.

Before integration: apply the task-owned adapter, shared auth helper, internal route and route-auth refactor; register the queue SQL only after its disposable pgTAP fixture passes; run task 20's authorization SQL/pgTAP for same-principal recapture semantics; then configure and observe a trusted scheduler. The capture helper copy preserves HTTP status and `Retry-After` while retaining the existing bounded pagination behavior. Keep `googleDriveViewerLinkEnabled()` off until the existing release gate is explicitly approved.

The five-item claim cap, 60–900-second freshness range, and bounded per-turn enqueue limit do not guarantee catch-up for a large workspace. At the two-thirds freshness trigger, only one third of the configured age remains; if the eligible backlog exceeds measured provider/API capacity in that interval, some snapshots become stale and authorization must stay fail-closed. Queue uniqueness coalesces concurrent work per workspace/connection/source-version and capped retry delays prevent a single worker turn from waiting indefinitely, but they do not create throughput. There is no schedule or readiness claim until the actual eligible-file count, provider latency/429 rates, polling cadence, and worker concurrency have demonstrated adequate headroom.

**Storage-growth limitation:** each successful complete capture inserts a new immutable ACL observation, including an unchanged hash, so historical evidence for frequently refreshed files grows with capture count. Queue uniqueness bounds duplicate pending work for one source version, but does not bound accumulated snapshot observations or rows for obsolete source versions. Do not enable routine refresh at scale until an explicit, tested retention policy can safely remove only observations no longer pinned or referenced by active jobs. No retention limit or history deletion is included in this candidate; retaining every immutable observation forever is not a bounded storage plan.

Focused follow-on validation passed: TypeScript project check, ESLint on changed application files, 19/19 Node decision-core tests, and 69/69 focused Vitest tests across four files. pgTAP was not run because it requires a disposable database; no database or provider was contacted. The new SQL assertions still require execution in a disposable database before draft registration.

## Candidate artifacts

- `nextjs/lib/google-drive-acl-refresh.ts`: app adapter reusing existing OAuth secret/runtime, customer-data admission, source ACL capture and snapshot-record functions; it enqueues at most 100 bindings per cursor page and claims only work that fits the remaining per-turn budget, currently at most one.
- `nextjs/app/api/internal/jobs/acl-refresh/route.ts`: one bounded, no-store worker turn behind the existing worker Bearer credentials. No recurring scheduler is configured.
- `nextjs/lib/internal-worker-auth.ts` and the `nextjs/app/api/internal/jobs/run/route.ts` candidate copy: shared implementation of the existing worker auth check, with the existing sync route using that same helper.
- `nextjs/lib/acl-refresh-core.mjs`, `nextjs/lib/acl-refresh-core.d.mts`, and `nextjs/lib/acl-refresh-core.test.mjs`: bounded decision core and offline Node tests for empty change feed, dedupe, no byte download, revoked admission, leases, capture incompleteness, 429 backoff, latest-ACL authorization and separate viewer-link expiry.
- `nextjs/lib/google-drive-acl-capture.ts`: exact base capture module copy with typed HTTP status/`Retry-After` propagation for queued backoff.
- `nextjs/lib/google-drive-acl-refresh.test.ts` and `nextjs/lib/internal-worker-auth.test.ts`: application-native Vitest coverage for the adapter and shared auth gate.
- `supabase/drafts/google-drive-acl-refresh/tests/google_drive_acl_refresh_queue.sql`: disposable pgTAP fixture for due discovery, dedupe, bounded lease claims, token ownership, retry caps, append-only recapture and marker behavior, viewer denial, and tied latest captures, incomplete-to-complete recovery, cleanup cursor wraparound, and per-connection cooldown; intentionally outside Supabase test discovery.
- `supabase/drafts/google-drive-acl-refresh/queue.sql`: service-role-only draft queue contract with finite cursor-paginated cleanup/inventory scans, bounded claims, durable connection cooldown, lease completion, and current-binding discovery. It is intentionally not a registered migration.
