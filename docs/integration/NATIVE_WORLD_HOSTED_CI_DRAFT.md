### Automatic PR 141 checks

Once this workflow is on the PR 141 head branch, every `opened`, `synchronize`
or `reopened` event of PR 141 runs it automatically. No dispatch is needed.
Any other pull request into `main` triggers the workflow, but both jobs are
skipped by the guards. If a guard were bypassed, `admit` would still refuse it.
Refused cases include a fork, another PR number, another head or base branch,
another repository, a `pull_request_target` or push event, and a checkout
`HEAD` that differs from the payload PR head SHA. The contract suite covers
each of these.

On PR runs the case receipts, the aggregate receipt and the expected harness
identity (`checkoutHead`) are bound to the PR head SHA, not to the merge-ref
`github.sha`. Receipts also record `event` and `ref`. Aggregation requires
`pull_request` and `refs/pull/141/merge` on PR runs, and `workflow_dispatch`
and `refs/heads/main` on manual runs. A receipt from one path cannot satisfy
the other. Manual dispatch on `main` keeps its `github.sha` binding unchanged.

None of this has run. Whether the first automatic PR 141 run passes is
unknown until GitHub runs it. This patch does not dispatch the workflow or
trigger any PR event.

## Setup sequence for each matrix job (623 semantics)

There are seven matrix jobs, one fresh `ubuntu-24.04` VM per case:
`grant_revoke`, `qualification_revoke`, `epoch`, `delete`, `same_replay`,
`changed_replay` and `member_fk`. `fail-fast` is off.

1. Check out the bound commit (`github.sha` for manual runs, the PR head SHA
   for PR 141) and run `admit`.
2. Install Supabase CLI `2.116.0` and verify the version. Every job sets
   `SUPABASE_INTERNAL_IMAGE_REGISTRY=docker.io`.
3. Run `stage`:
   1. Write `supabase/config.toml` (`project_id = "tavonel_native_world_race"`,
      `[db] major_version = 17`). It is created exclusively, so an existing file
      is never overwritten.
   2. Create each migration with `supabase migration new <slug>`. The new file
      must be the only new file, start empty, and have a 14-digit UTC version
      strictly greater than the previous dependency and every existing version.
   3. Byte-copy each pinned draft into its migration, compare the bytes, and
      record the result.
   4. Stage the migrations in this order:
      1. `google-viewer-principal-boundary.sql` (`8aad3ff…06bc`). This
         assumes the "viewer ACL boundary" pin is for this file. If it is not,
         admission fails.
      2. `google-drive-acl-refresh/queue.sql` (`04b7593…c4a8`).
      3. `compile-job-viewer-authority.sql`, checked by Git blob `f9221ed…319c`.
      4. Intake triage v3 (`092247c…7a00e`).
      5. Completed-read proof (`c92a565…8163`).
      6. Native source ledger snapshot (`08fc0ba…c258`).
      7. Native purpose authority schema (`9763468…3268`).
      8. Native purpose candidate reader (`84f2e7f…75e2`).
      9. Native World SQL (`de039c9…a4db`).
   5. After the migrations, copy the pgTAP sources exclusively and byte-for-byte:
      - The ACL refresh test.
      - The intake and completed-read tests.
      - The four native tests.
      - The World unit wrapper, generated exclusively at
        `supabase/tests/native_world_reduction_commit.sql` (see above).
   6. Check that `supabase/tests/compile_job_viewer_authority.sql` exists and
      matches Git blob `b2c9e95…2be`.
   7. Check that `supabase/tests/google_viewer_principal_boundary.sql` exists.
      No pin was supplied for it, so only its presence is checked.
   8. Write the stage receipt to `$RUNNER_TEMP/native-world-race/`.
4. Reset sequence, copied from the 623 baseline:
   1. Move every `supabase/migrations/*.sql` with a version above `0048` to
      `/tmp/deferred-migrations` and record their SHA256 values.
   2. Run `supabase db start` with the pre-boundary chain.
   3. Restore the deferred files and verify their SHA256 values.
   4. Run `supabase db reset` to apply the full chain from empty.
5. Run `capture`. This is the owner's only name resolution
   (`supabase_db_tavonel_native_world_race`). It requires:
   - A running container.
   - The image `supabase/postgres:17.6.1.165`, with or without the `docker.io/`
     prefix, and a `sha256:` image digest.
   - A 64-hex container ID.
   - One local named data volume at the expected mountpoint, with no driver
     options and no consumer except this container.
   - Mount confinement that matches the frozen harness's `validateContainer`.
     Exactly one mount may have destination `/var/lib/postgresql/data`.
     Every other `Mounts` entry and every `HostConfig.Tmpfs` key must be an
     absolute path. After normalization (dot segments and trailing slashes),
     none may equal, contain or sit inside `/var/lib/postgresql/data`,
     `/var/run/postgresql` or `/run/postgresql`. A non-object `Tmpfs` is
     refused. Unrelated mounts are allowed.

   Only then does it open one SQL session, in a read-only transaction, by the
   captured ID. It requires `server_version` 17.6,
   `data_directory = /var/lib/postgresql/data` and exactly
   `unix_socket_directories = /var/run/postgresql`. Any refusal happens before
   any marker write, extension creation or other mutating SQL. It also happens
   before `setup.json` exists, so finalize has no cleanup authority and touches
   nothing.

   Then, in order:
   1. It writes a fresh `tavonel-disposable-<uuid>` marker through
      `docker exec <captured-id> psql` into
      `tavonel_ci_fixture.disposable_marker`, creating the table if it does not
      exist, and requires exactly one row.
   2. It sets up pgTAP as in 623:
      `create extension if not exists pgtap with schema extensions`. It then
      requires that the `pgtap` extension's namespace is `extensions` and that
      the extension owns exactly the required functions `no_plan`, `ok`, `is`
      and `finish` there.

   `setup.json` is rewritten only after each step validates. `run-harness`
   refuses evidence that has no marker or no verified pgTAP setup.
6. Run `run-harness`. This runs `node nextjs/scripts/db/native-world-race.mjs`
   once, in its own one-case mode. The environment contains only the documented
   variables: `NATIVE_WORLD_RACE_*`, `RUNNER_ENVIRONMENT`, `GITHUB_ACTIONS`,
   `GITHUB_RUN_ID`, `GITHUB_RUN_ATTEMPT`, `GITHUB_JOB`, `PATH=/usr/bin:/bin`,
   `HOME` and `LANG`. No Docker/PG redirect, credential or token variable is
   passed. The step is limited to 5 minutes. That is the owner's wall-clock
   limit, not the harness's 120-second run budget. The harness writes its
   receipt under the job workspace (`native-world-race-receipts/`), which is
   never committed.
7. Run `finalize` (`if: always()`). It performs owner cleanup, then writes
   `case-receipt.json` to `$RUNNER_TEMP`, and it is uploaded as artifact
   `native-world-race-<case>`.

## Owner cleanup contract

Owner cleanup always runs, but it acts only on validated setup evidence bound to
this head, run ID, attempt and case. The evidence must contain:

- The exact `supabase_db_<project>` name and a captured 64-hex ID.
- The pinned image reference and digest.
- A local named volume with its exact `{name, driver, scope, createdAt, mountpoint}`.
- The validated server settings (`17.6`, the data directory and the single
  socket directory).

All Docker calls go through `/usr/bin/docker --host unix:///var/run/docker.sock`
with a filtered environment. Steps, in order:

1. List containers by the captured ID. If present, inspect it fresh by that ID,
   never by name. Check its identity, image and digest, and the full mount/tmpfs
   confinement described above. If the layout now overlaps, everything is kept.
2. Require that the captured ID is the volume's only consumer and that the
   volume identity is unchanged.
3. If the container is running, first run one fresh read-only PostgreSQL
   settings query by the captured immutable container ID, never by name. It
   requires `server_version` 17.6, `data_directory = /var/lib/postgresql/data`
   and exactly `unix_socket_directories = /var/run/postgresql`, each in exact
   agreement with the captured identity. If the query fails or any setting has
   drifted, the container and volume are kept, no destructive cleanup runs and
   the query is not retried. Only after it passes, stop the container and
   inspect it again. For a stopped container, the validated capture evidence is
   sufficient and no SQL runs.
4. Run plain `docker rm <id>` (no `-f` or `--volumes`).
5. If `rm` fails, inspect the exact stopped ID and the volume identity again,
   then retry plain `rm` once. This retry is teardown only. **SQL is never
   retried, and the harness is not re-run.**
6. Require that the volume has zero consumers and the same identity, run
   `docker volume rm <captured volume>`, and check that it is gone.

If any check fails, the resources are kept and the problem is recorded under
`residuals`. Missing or malformed evidence leaves everything untouched. If the
harness stopped the container but failed to remove it, owner cleanup can finish
the teardown, but the case still fails because the harness gate is `failed`.
Proving that case again needs a new dispatch.

## Receipts and aggregation

Each case receipt records:

- Repository, event, ref, checkout head (the bound head), run ID and attempt,
  job (`race`) and case.
- The frozen input, fixture and schema hashes.
- The exact stage receipt text and its SHA256.
- The marker SHA256.
- The complete owner-captured target: container name and ID,
  `imageReference`, `imageDigest`, the full volume identity
  `{name, driver, scope, createdAt, mountpoint}`, the server settings and the
  pgTAP evidence.
- The harness exit code and the raw harness receipt with its SHA256.
- The harness's own cleanup result and the owner cleanup result.
- `fullQualification: pending` and `reservationExpiryCrossSession: UNRUN`.

`aggregate` does not trust any stored `pass` flag; it rechecks every receipt.
It requires all of the following:

- The matrix result is `success`.
- Exactly seven `case-receipt.json` files are present, one per case, with each
  artifact name matching its case.
- Every receipt matches the aggregate job's event, ref, bound head, run ID and
  attempt.
- Every harness receipt has an intact hash, gate
  `passed-one-synthetic-cross-session-case`, `actual-container-postgres`, one
  case that matches the receipt and passed, harness cleanup removed, no
  failures, matching head, run and job, and the pinned harness, fixture and
  schema hashes.
- The SHA256 of the preserved stage receipt bytes equals `stageReceiptSha256`.
  The stage receipt content also matches the shipped plan:
  - Config hash.
  - Migration order, slugs and source pins.
  - Byte-identical migration copies under strictly increasing 14-digit
    versions.
  - Test copy pins.
  - The generated unit wrapper with SHA256 `04a09fc…5a`.
- The owner target has exactly the validated fields:
  - A pinned image reference and a `sha256:` digest.
  - A local volume with local scope, a parseable `createdAt` and the expected
    mountpoint.
  - Server `17.6` with the qualified data and socket directories.
  - pgTAP in `extensions` with `no_plan`, `ok`, `is` and `finish`.

  Any missing, extra or altered field fails.
- The harness preflight capture equals the owner capture field by field:
  - ID, image digest and image reference.
  - Data volume name and source.
  - Full volume identity.
  - Server settings and server version.
  - Marker hash.
- Owner cleanup is `verified-absent` with no residuals.
- Container IDs, markers and harness receipts are all distinct across cases.

Missing, duplicate, skipped, failed, tampered or mismatched evidence makes the
gate `failed`. A passing aggregate means seven synthetic cross-session cases
passed. It does not mean full qualification.

## Risks and reviewer items

- Third-party actions use major-version tags (`actions/checkout@v4`,
  `supabase/setup-cli@v1`, `actions/upload-artifact@v4`,
  `actions/download-artifact@v4`), as the 623 baseline does. If the operator
  requires immutable action refs, review them and pin them to immutable action
  commit SHAs before enabling. This draft does not guess those SHAs.
- The marker step creates `tavonel_ci_fixture.disposable_marker(value text
  primary key)` if it is absent, and it assumes the `postgres` role can do this.
  Confirm this against the existing contract.
- The pgTAP statement was written from the stated 623 setup (schema
  `extensions`). The 623 workflow text was not available in this session, so it
  was not compared line by line. It also assumes the `postgres` role may create
  the extension. Confirm both before enabling.
- The aggregator assumes `writeReceiptOnce` stores the harness report as plain
  JSON at the path the harness prints. If it wraps the report, aggregation fails
  closed.
- Re-running only the failed jobs changes the run attempt, which fails
  aggregation. Dispatch the workflow again instead (for PR 141, re-run all jobs
  or push a new head).
- The PR binding assumes that the frozen harness reports `checkoutHead` from the
  checked-out `HEAD`, which is the PR head SHA on PR runs. The harness gets no
  event, ref or `GITHUB_SHA` variable, and its source is unchanged. If it
  derives `checkoutHead` differently, PR aggregation fails closed.
- The PR 141 guards and payload checks use the base, head and event repository
  names and IDs from the runner-written payload. They have not been compared
  with a live PR 141 payload.
- If a job is aborted, resources can be left on the VM. The hosted VM is
  discarded at the end of the job.
